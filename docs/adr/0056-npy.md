# ADR 0056: NumPy `.npy` files

Status: accepted, 2026-11-13

## Context

Random streams differ between the two languages, so cross-language checks on noisy signals
exchange the samples as files. SigMF works but needs two files and a metadata document. The `.npy`
format is what NumPy users save arrays in, and it is a short text header followed by the raw
array, simple to write and read by hand.

## Decision

- `write_npy(path, x)` and `read_npy(path)` in `signalforge.files` (C# `SignalFiles.WriteNpy`,
  `ReadNpy<T>`). Only 1-D little-endian `float64` (`'<f8'`) and `complex128` (`'<c16'`) arrays:
  what both languages compute in. Arrays, not signals: an `.npy` file has no sample rate.
- Writing makes one layout, the one NumPy itself writes for these arrays: version 1.0, the header
  `{'descr': '<f8', 'fortran_order': False, 'shape': (n,), }` padded with spaces and a newline so
  the data starts at byte 128. Files written here and by `numpy.save` are the same bytes, which the
  Python tests check, and NumPy reads them.
- Reading takes versions 1.0, 2.0 and 3.0 and parses the header with a small grammar of its own,
  the same in both languages, instead of evaluating it as Python: a dict of exactly `descr`,
  `fortran_order` and `shape`, strings in either quote, `True`/`False`, and a tuple of decimal
  integers. Anything else, another dtype, more or fewer than one dimension, or a data size that is
  not exactly the shape, is rejected. `fortran_order` does not change a 1-D array, so either is
  read.
- In C# the element type is the type argument, as for `DecodeSamples<T>`, and a file of the other
  kind is rejected.

## Consequences

- A noisy run can be saved in one language and read in the other, or in NumPy, with one call.
- Other dtypes, multi-dimensional arrays and `.npz` archives are not read; they can be added
  later without changing what is written.
