# ADR 0089: NumPy `.npz` archives

Status: accepted, 2026-11-14

## Context

`numpy.savez` and `numpy.savez_compressed` bundle several arrays into one file: a ZIP archive with
one `.npy` member per array, named `<key>.npy`. Datasets and test captures often travel that
way: IQ next to its taps, or a set of channels. SignalForge reads and writes single `.npy` files
([ADR 0056](0056-npy.md), [ADR 0088](0088-npy-read-dtypes.md)). Both standard libraries can
already decompress deflate (Python `zlib`, .NET `System.IO.Compression.DeflateStream`), so neither
language needs a new dependency.

## Decision

- **API**: `write_npz(path, arrays)` and `read_npz(path)`. C#: `WriteNpz(path, arrays)` and
  `ReadNpz(path)`. In Python `arrays` is a mapping from name to a 1-D array, and `read_npz`
  returns a `dict`. In C# the values are `double[]` or `Complex[]` typed as `Array`: `WriteNpz`
  takes `IEnumerable<KeyValuePair<string, Array>>`, and `ReadNpz` returns an
  `OrderedDictionary<string, Array>`. Both keep the archive's member order.
- **The ZIP is laid out and parsed by SignalForge itself**, not by `zipfile` or `ZipArchive`. The
  two libraries write different bytes, and they accept different archives (`zipfile` also
  decompresses bzip2 and LZMA, `ZipArchive` Deflate64). Laying the ZIP out by hand gives the two
  languages the same bytes and the same rejections. Only the deflate decoding is the library's.
  CRC-32 (the ZIP polynomial, reflected `0xEDB88320`) is computed by SignalForge in C# and with
  `zlib.crc32` in Python.
- **Writing** is what `numpy.savez` stores, without its ZIP64 extra fields and timestamps, so a
  write is reproducible:
  - each member is uncompressed, with the `write_npy` bytes for that array;
  - the time is 00:00 and the date 1980-01-01;
  - there are no extra fields, comments or data descriptors.
  Names must be 1 to 250 printable ASCII characters (0x20–0x7E), with no `/` or `\`, and each
  name is used once. The archive must stay under 4 GiB with at most 65535 members, because
  ZIP64 is not written.
- **Reading** takes what `numpy.savez` and `numpy.savez_compressed` write, and other writers'
  plain archives:
  - Methods 0 (stored) and 8 (deflate) are read.
  - The central directory is the authority, and data descriptors are allowed. A ZIP64 extra field
    supplies a size or offset whose 32-bit field is `0xFFFFFFFF`; NumPy writes these.
  - Rejected:
    - encryption (flag bit 0);
    - any other method;
    - a multi-disk archive;
    - an archive that needs the ZIP64 end record;
    - a CRC mismatch, or a member that does not inflate to its uncompressed size;
    - a member whose name does not end in `.npy`, or a key used twice.
  - Each member's bytes are read as `read_npy` reads a file, every accepted dtype included.
  - Names are UTF-8 when flag bit 11 is set, and otherwise must be ASCII.
- **Expected values**: the npz generator lays out the ZIPs with `struct` and `zlib.crc32`, and
  deflates members with `zlib` at several levels. It also writes the ZIP64-extra local and central
  headers in the shape `numpy.savez` writes. The Python tests read real `numpy.savez` and
  `numpy.savez_compressed` output.

## Consequences

- A `.npz` from `numpy.savez` is read without NumPy's pickle path, and a file SignalForge writes
  loads with `numpy.load`.
- Archives over 4 GiB are not read or written.
