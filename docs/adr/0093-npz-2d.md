# ADR 0093: 2-D `.npz` members

Status: accepted, 2026-11-14

## Context

`.npz` archives ([ADR 0089](0089-npz.md)) hold 1-D members only, so an archive with a matrix in it
(a filter bank next to its input, a set of channels saved as one array) cannot be read, even
though `read_npy_2d` ([ADR 0092](0092-npy-2d.md)) reads the same member as a lone file. NumPy's own
archives freely mix shapes: `numpy.savez(f, taps=h, bank=H)` with `h` 1-D and `H` 2-D.

## Decision

- **Each member keeps its own dimensions.** `read_npz` returns a 1-D member as before and a 2-D
  member as a 2-D array: in Python a C-ordered 2-D `float64` or `complex128` array in the `dict`,
  in C# a `double[,]` or `Complex[,]` in the `OrderedDictionary<string, Array>`. One archive may
  mix 1-D and 2-D members. A 2-D member is read as `read_npy_2d` reads a file, Fortran order and
  the 2147483591 dimension limit included; 0-D and 3-D members or more are still rejected.
- `write_npz` takes 1-D and 2-D values (C#: also `double[,]` and `Complex[,]`), each written with
  the bytes `write_npy` writes for it, so a 2-D member is in C order.
- No separate `read_npz_2d`: the C# values are already typed `Array`, which carries its rank, and
  a separate reader could not read a mixed archive.

## Consequences

- A 2-D member, which `read_npz` rejected until now, is read instead. Code that relied on that
  error must check the rank (`ndim` in Python, `Array.Rank` in C#).
- Shared vectors pass a 2-D member as `{name, shape, x}` with `x` flat in C order, as the 2-D
  `.npy` vectors do; a 1-D member stays `{name, x}`.
